# Live 人物上下文双账号验收

[返回语音指南](voice-guide.md)

适用于包含 `850c03b` 人物诊断功能的 `dev` 版本。使用部署机上的正常语音台，验证人物映射、连续追问、回答内容和抢话。每个房间保留一个 Gemini Live 会话。

双账号指 A、B 两个发言账号，另加现有机器人账号，共三个账号。准备一个独立测试房，A、B 使用耳机，关闭背景音乐，记录两人的 Oopz UID。实际账号、模型和音频效果由以下步骤在部署机验收。

1. **更新并开启预览**

   在控制台的更新与备份中选择 `dev`，更新并重启 Ooptra。使用 Git 部署时，可在项目目录运行 `git rev-parse --short HEAD` 记录提交，并确认当前代码已包含 `850c03b`。

   进入「配置 → 语音模型」，开启语音，沿用原来能正常工作的 Gemini Live 模型和凭据，设置下表中的测试值。

   | 设置 | 测试值 |
   | --- | --- |
   | 语音后端 | Gemini Live |
   | Live 人物上下文（预览） | 开启，位于高级选项的「行为」分组 |
   | 语音回复频率 | `0%` |
   | 强制回复关键词 | `机器人` |
   | 连续对话窗口 | 开启，`30` 秒 |
   | 允许抢话打断 | 开启 |
   | 抢话门限 | `300` 毫秒 |
   | `listen_only_uids` | 先留空 |

   保存后让机器人重新进入测试房，展开「语音台 → 会话」中的「Live 人物与回合」。同一组测试期间保持这个房间会话，修改模型配置或刷新模型上下文后重新开始该组测试。

2. **验证人物对应**

   A、B 依次说一句完整的话。每句之间等上一轮模型回合完成、迟到转写收尾结束。这组发言没有关键词，机器人保持安静符合预期。

   | 发言 | 核对结果 |
   | --- | --- |
   | A 说“我是测试成员 A，现在开始测试” | `input_start` 对应 A 的 Oopz UID |
   | B 说“我是测试成员 B，现在开始测试” | `input_start` 对应 B 的 Oopz UID |
   | A 再说一句不同内容 | 仍对应 A |

   查看“已确认音轨”中的 `Agora UID → Oopz UID`，与「房间成员」中的两人 UID 比较，昵称用于辅助辨认。较短的发言可能已经结束，可从导出的 `recent_events` 检查归属。

   **通过标准**是 A、B 都能确认身份，互不交换，相关事件中的 `source.confirmed` 为 `true`。

   如果显示“身份待确认”，让两人各切换一次麦克风状态再测。仍无法确认时，导出诊断并记录为映射未通过。

3. **验证连续追问与回答内容**

   按下表顺序进行，A 的追问须在 30 秒窗口内。每一步都等上一轮处理结束。

   | 顺序 | 谁说什么 | 预期 |
   | --- | --- | --- |
   | ① | A：“机器人，这一轮我选红伞，请简短回应。” | 机器人回复，A 开启追问窗口 |
   | ② | B：“这一轮我选蓝船。” | 机器人保持安静 |
   | ③ | A：“我刚才选的是什么？” | 无需关键词也回复，答案是“红伞” |
   | ④ | B：“我刚才选的是什么？” | 仍保持安静，B 没继承 A 的窗口 |
   | ⑤ | B：“机器人，我刚才选的是什么？” | 回复“蓝船”，B 开启自己的窗口 |

   做完③导出一次，做完⑤再导出一次。接着等 A 最近一轮结束 35 秒，让 A 再说一句不带关键词的普通追问，应保持安静，并再保存一份诊断。

   **通过标准**同时包括播放策略和回答内容。即使 UID 正确，若把 B 的“蓝船”回答给 A，也记为串人失败。

   `reply_decision.reason` 可辅助检查关键词、追问窗口或概率跳过。若转写迟到后才触发补播，结合 `late_transcription`、`first_audio` 和实际听感判断，并保存当时日志。

4. **验证抢话和句首保留**

   先导出上一组诊断，再让机器人退房、重新进房，清空追问窗口，并确认人物映射恢复。

   - A 说“机器人，请从一数到二十。”
   - 机器人开始出声后，B 正常、连续地说至少一秒：“蓝船，机器人，请只回答收到。”
   - 听旧回复是否及时停止，随后是否响应 B，旧回复是否又恢复播放。
   - 查看 `barge_in`，再核对 B 下一轮 `input_start` 的 UID。
   - 在「日志」的 `Live 回合` 转写中，检查 B 句首“蓝船”是否保留。

   再测一次短于门限的短促“嗯”，机器人应继续原回复。若短声也频繁打断，记录现象，再把门限调到 `600` 毫秒复测，保留两组结果及各自的门限。

   **通过标准**是持续讲话能停止旧播放，新一轮归 B，句首没有明显丢失，旧回复不会重新冒出来。抢话后的新回答可能还要等待旧模型回合收尾，同时记录这段等待。

5. **验证重新进房恢复**

   导出抢话诊断后，让机器人退房再进房，确认进房播报或手动开口能正常播放，A、B 仍能正确对应。

   重新进房后，先前的个人追问窗口应已清除，需要再次喊关键词唤醒。分别测试普通发言保持安静、带关键词后能回复，并保存诊断。

6. **保存验收材料**

   点击「Live 人物与回合 → 导出本次诊断」，下载默认的 `ooptra-live-speaker.json`，按测试组重命名。最近事件最多保留 40 条，建议每两三轮发言保存一次。发生问题时先导出，再退房、重启或刷新模型上下文。

   | 文件建议名 | 保存时机 |
   | --- | --- |
   | `01-人物映射.json` | 人物对应测试后 |
   | `02a-连续追问-A.json` | 完成步骤③后 |
   | `02b-连续追问-B.json` | 完成步骤⑤后 |
   | `02c-窗口过期.json` | 完成 35 秒过期检查后 |
   | `03-抢话-300ms.json` | 抢话结束后立即保存 |
   | `03b-抢话-600ms.json` | 调整门限复测后，如有 |
   | `04-重新进房.json` | 恢复检查后 |
   | `失败-时间-现象.json` | 出现问题后立即保存 |

   JSON 中重点查看以下字段。

   | 字段 | 用途 |
   | --- | --- |
   | `area`、`channel` | 核对测试房间 |
   | `mappings` | 已确认的 Agora UID、Oopz UID 与显示名 |
   | `current`、`pending` | 导出时当前和待处理的发言来源 |
   | `recent_events[].source` | 事件所属的 `rtc_uid`、`oopz_uid`、`confirmed`、`turn_id` |
   | `recent_events[].event`、`reason`、`outcome` | 回合事件与接话决策 |
   | `recent_events[].phase`、`error_kind` | 出错阶段和错误类别 |
   | `first_audio_ms`、事件的 `elapsed_ms` | 输入首帧到回复音频提交的耗时 |

   `first_audio_ms` 不代表远端扬声器实际出声的时间，实际听到声音的延迟另行记录。JSON 包含成员标识，不含音频、发言正文或模型凭据。

   同时保存测试时段的「日志」下载文件，并填写下面的验收记录。日志中的 `Live 发言开始` 可辅助关联轮次与 UID，`Live 回合` 可核对转写和回复内容。

```text
部署提交
测试日期、时间及所在时区
Gemini Live 模型名称
测试域、频道
A 的 Oopz UID、显示名
B 的 Oopz UID、显示名
回复概率、关键词、窗口秒数、抢话门限、silence_ms

每项用例
  测试时间
  谁实际说了什么
  机器人实际回答了什么
  是否停播、是否有旧回复恢复
  主观等待时间
  对应诊断文件与 turn_id
  结果（通过 / 未通过 / 未执行）
```

将人物映射、连续追问、窗口过期、抢话和重新进房逐项记录。若该次测试没有遇到迟到转写，记录“本次未观测到”，后续出现相关问题时再按事件和日志复核。
